# Employee Management Service

A REST API for departments, employees, manager relationships, and leave requests. It uses Express 5 and PostgreSQL through the `pg` connection pool. It is designed as a learning project with readable SQL, explicit database constraints, and comments that explain the important workflows.

## Features

- Create, read, update, and delete departments and employees.
- Every employee belongs to one department and may report to another employee. A top-level manager has no manager.
- Employees submit leave requests. Their assigned manager approves or rejects each pending request.
- Approval deducts inclusive calendar days from the employee's balance in the same transaction as the decision. Rejection does not change the balance.
- An approved leave cannot overlap another approved leave for the same employee. The approval flow serializes decisions for that employee to handle simultaneous requests safely.
- Reports return department headcount, employees on leave today, and the employee-to-top-manager chain.
- Employee search supports a case-insensitive name substring, department, and inclusive joining-date bounds.
- SQL schema migration and a repeatable seed script with 54 employees across six departments.

## Requirements and setup

- Node.js 20 or newer and npm
- PostgreSQL 13 or newer, with permission to create the `pgcrypto` extension

From this folder:

```powershell
npm install
Copy-Item .env.example .env
```

Edit `.env` with a PostgreSQL connection string, then create the database named in that string. For example, with a local PostgreSQL installation:

```sql
CREATE DATABASE employee_management;
```

Run the schema migration and sample data, then start the API:

```powershell
npm run migrate
npm run seed
npm run dev
```

The server listens at `http://localhost:3000/api/v1` by default. Set `PORT` to change the port. Set `DATABASE_SSL=true` only for a hosted PostgreSQL endpoint that requires TLS. `npm run seed` removes existing employees before creating its sample organization; do not run it against data you need to preserve.

## Database design

The schema is in [`migrations/001_initial_schema.sql`](migrations/001_initial_schema.sql). It defines UUID primary keys, unique department names and employee emails, foreign keys, check constraints, and indexes for employee name, department, joining date, manager relationships, and leave searches. Migrations are tracked in `schema_migrations`, so a successfully applied migration is not run again.

The ER diagram is in [`docs/er-diagram.md`](docs/er-diagram.md) and uses Mermaid syntax. Seed records are generated by [`scripts/seed.js`](scripts/seed.js); all generated SQL values are passed as parameters.

## API conventions

All paths below are relative to `/api/v1`. Successful responses use `{ "success": true, "data": ..., "error": null }`. Errors use `{ "success": false, "data": null, "error": { "message": "..." } }`. Validation errors are 400, missing records are 404, and rule or constraint conflicts are 409. Deletes return `204 No Content`.

All SQL values use PostgreSQL parameters (`$1`, `$2`, ...). Search filters use a fixed SQL statement and nullable parameters. There is no authentication in this learning API; the `managerId` on a leave decision is supplied by the caller and is checked against the employee's assigned manager, but a real deployment must derive the caller identity from authenticated credentials.

### Health and departments

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/health` | Check API and database connectivity |
| GET | `/departments` | List departments |
| POST | `/departments` | Create department: `{ "name": "Engineering", "description": "..." }` |
| GET | `/departments/:id` | Get one department |
| PUT | `/departments/:id` | Replace department name and description |
| DELETE | `/departments/:id` | Delete an empty department |

Deleting a department that still has employees returns `409` with a clear instruction to reassign or remove them first.

### Employees

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/employees` | List or search employees |
| POST | `/employees` | Create employee |
| GET | `/employees/:id` | Get one employee with department and manager names |
| PUT | `/employees/:id` | Replace employee profile fields |
| DELETE | `/employees/:id` | Delete employee |

Employee creation requires `firstName`, `lastName`, `email`, `departmentId`, and `joiningDate`. Optional fields are `managerId`, `jobTitle`, and `leaveBalance` (defaults to 20 days). For example:

```json
{
  "firstName": "Morgan",
  "lastName": "Lee",
  "email": "morgan.lee@example.com",
  "departmentId": "00000000-0000-0000-0000-000000000000",
  "managerId": "00000000-0000-0000-0000-000000000000",
  "jobTitle": "Analyst",
  "joiningDate": "2025-02-10",
  "leaveBalance": 20
}
```

Search query parameters are optional and combine together: `name` (case-insensitive substring over first and last name), `departmentId` (UUID), `joinedFrom` and `joinedTo` (ISO dates, inclusive). Example: `/employees?name=lee&departmentId=<uuid>&joinedFrom=2024-01-01&joinedTo=2025-12-31`.

### Leave requests

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/leave-requests?employeeId=:id` | List requests, optionally for one employee |
| POST | `/leave-requests` | Apply for leave |
| POST | `/leave-requests/:id/decision` | Manager approves or rejects |

Submit `{ "employeeId": "<uuid>", "startDate": "2025-08-11", "endDate": "2025-08-13", "reason": "Personal leave" }`. Both dates count toward the balance. A manager decides with `{ "managerId": "<manager-uuid>", "decision": "approved" }` or `"rejected"`. Only the employee's currently assigned manager can decide. Decisions are final; a decided request cannot be changed. An overlap or insufficient balance returns `409`, and a failed approval leaves the balance unchanged.

### Reports

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/reports/headcount` | Headcount by department, including empty departments |
| GET | `/reports/on-leave-today` | Employees with approved leave covering the current database date |
| GET | `/reports/hierarchy/:employeeId` | Employee, then each manager up to the top level |

The hierarchy endpoint uses a PostgreSQL `WITH RECURSIVE` query and includes a `level` field (`0` is the requested employee). A visited-ID guard prevents an accidental manager cycle from looping forever.

## Project layout

```text
src/
  app.js             Routes, request validation, transactions, and error responses
  db.js              Shared PostgreSQL connection pool
  server.js          HTTP server lifecycle
migrations/          Versioned PostgreSQL schema changes
scripts/
  migrate.js         Applies each migration once
  seed.js            Creates six departments and 54 sample employees
docs/er-diagram.md   Mermaid entity relationship diagram
```

## Notes

- This project intentionally does not include authentication, role management, pagination, or an audit trail. Add those before using it with real employee information.
- Deleting an employee also deletes that employee's leave requests; employees who report to them have their `manager_id` set to `NULL`.
- Department IDs and sample email addresses are generated data. Use the API responses to obtain IDs for follow-up requests.
